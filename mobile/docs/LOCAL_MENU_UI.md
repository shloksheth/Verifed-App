# Local menu interface

The native app opens on Orlando restaurant discovery. Home and Explore use real restaurant records marked `fictional: false`; the default Explore view is a compact restaurant list. It shows the street address, number of included entries and the location's congressional district. Local menus and Sample kitchens are separate catalog tabs, followed by Restaurants and Menu items views. Search matches restaurant names, addresses, menu names, descriptions and tags. Category tabs apply to menu items; the known-conflict checkbox keeps unknown information visible.

Area choices come from the actual `restaurant.district` records. All Orlando is the default. A single-district catalog shows a compact location caption instead of a redundant selector; multiple districts expose an Area filter. These describe restaurant locations, not the diner's location. Changing catalog or area resets the category to avoid leaving an unavailable category selected. Restaurant source panels retain the district's Congress and evidence link.

Restaurant detail is an editorial menu with a large serif restaurant wordmark, a location line, a fine accent rule and category sections separated by thin dividers. Hawkers uses a warm red accent, Fresh Kitchen a dark green and Chipotle a burgundy. Menu rows show the item, reported price or Check menu, a short description and declared-allergen symbols. Components are explicitly labeled. Rows open the existing dish detail, where full evidence remains available. Restaurant menu rows do not repeat the large assessment warning card.

The compact source area keeps the address, review scope/date and inline Official menu, Call and Sources actions. Sources is collapsed by default. Expanding it reveals the evidence note, allergen information, website, phone number and district metadata/source. These actions open through React Native Linking; phone links open `tel:` actions. Links display errors from the platform if opening fails. Chainwide evidence is distinguished from location-specific evidence. A source review date is not a restaurant confirmation.

Each restaurant offers **For my diet** and **Full menu** with a clearly filled selected tab. Full menu is the default when no allergies or restrictions are selected. It renders every current catalog item grouped by the restaurant's source category, preserving source order. It does not claim to be a complete branch inventory: the count says cataloged food items, local availability is unconfirmed, and What this menu covers expands the source scope from `restaurant.menuCoverage`.

When dietary needs exist, For my diet is the default. It calls `dietaryMenuStatus(dish, profile)` from `src/menu-filter.js`; only `match` items enter Restaurant-reported matches. Unknown items are grouped separately behind Needs confirmation, with the missing requirements on each expanded row. Positive known conflicts are excluded from the matches and counted separately. With no needs selected, the dietary view prompts the diner to choose allergies or restrictions. The compact needs strip can edit the profile and return directly to the same restaurant. Restaurant-reported matching stays separate from `assessDish`; it never certifies preparation or cross-contact.

Strict matched rows show a selected-needs support line such as **Reported: Milk-free · Soy-free · Vegan**. They retain all known declared-allergen symbols, while generic Unknown and empty-declaration text is suppressed only in this section. One section note explains that matches cover selected needs and other allergens/preparation may require confirmation. Full menu and Needs confirmation retain the default unknown and empty-declaration presentation. Matching logic is unchanged.

`components/AllergenIcons.js` draws native SVG symbols for Milk, Egg, Fish, Shellfish, Tree nuts, Peanuts, Wheat, Soy and Sesame. Every symbol has written text and an accessibility label. A question mark labeled Unknown indicates incomplete source coverage of the nine tracked allergens. The expandable Allergen key explains all symbols. The same icons appear on Explore/favorite DishCards. No meaning depends only on color. A shared note explains restaurant-reported information and cross-contact once above the restaurant menu instead of warning on every row.

`otherDeclaredAllergens` remains visible in both menu tokens and dish details. A separate generic declaration symbol carries the source's exact written label, including Sulphites and Nuts (type unspecified). These declarations are never silently mapped to Tree nuts or Peanuts. Blank declaration lists say **No allergens declared; check details**, including when the source lists all nine coverage categories; blank cells do not establish absence.

The two menu modes set explicit `aria-selected` alongside native `accessibilityState`. Source, allergen-key, coverage and confirmation toggles also set `aria-expanded`; profile selection chips set `aria-checked`. These explicit web attributes keep assistive-technology state aligned with the visible UI when React Native Web does not map `accessibilityState` into the DOM.

Menu items use text rows instead of large emoji images. Missing prices read **Check menu**. Assessments have known-conflict, unknown, and review language; no item is labeled safe. Detail shows the recorded ingredients, declared allergens, preparation information, evidence note, review date, allergen coverage and source free-from claims. Empty declarations do not establish absence. Source claims are accompanied by a reminder that they do not establish cross-contact conditions at this location.

Entries whose provenance kind is `component` are labeled as one component, not a complete order. Detail asks the diner to assess all chosen bases, proteins, toppings, sauces and wraps. These records do not silently represent a complete configured meal.

Real menu detail offers direct restaurant calling and original sources. It never opens a simulated kitchen request, even if a real entry were accidentally marked `confirmed`. Sample kitchen requests remain a distinct practice flow. Favorites and meal journaling call the existing API with the original catalog IDs.

Guests can open the profile editor and apply `api.previewProfile(draft)`. This saves browsing preferences only on this device, without claiming an account save or sending information to a restaurant. Clear browsing profile resets these preferences through the same API. Signed-in and demo profile edits continue to call `api.saveProfile`. The App route allows guests into ProfileEditor.

When signed-in catalog loading falls back to a public record that has no database ID (`provenance` present and `cloudBacked` false), favorite controls are disabled. Detail offers **Refresh to save** rather than attempting a database write with a text catalog key. The API also guards this case.
