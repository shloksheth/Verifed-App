# Orlando catalog: how the real menus work

## Files and data flow

`src/local-catalog.js` adapts the reviewed public source catalog: three physical restaurants and 110 food records. Hawkers contributes 49 entries from its dining page, Fresh Kitchen 35 components/bowl formats/snacks, and Chipotle 26 standard components. `src/restaurant-menus.js` contains the readable source records generated by `research/build-menu-catalog.mjs` from `research/full-menu-data.json`. The generator rejects duplicate keys, invalid categories and contradictory positive/negative allergen claims. `research/full-menu-evidence.md` describes scope and item evidence. This is published food information, not a complete live branch inventory. Drinks, certain specials, kids or guide-only items may be outside the cited source; each restaurant discloses its coverage. Prices stay null because no current branch prices were verified.

Each restaurant has its address, telephone, official menu, allergen source, source review date and district evidence. Each dish has a stable `catalogKey`, positive allergen declarations and `provenance`. Provenance records whether an entry is a component or dish, which categories its source covers, explicit free-from claims, and evidence notes. Fresh Kitchen ingredient lists are transcribed from the September document. `ingredients: []` on other entries means the app did not transcribe a complete recipe; the detail screen says that explicitly. Prepared blends are not expanded into invented recipes. Other declarations such as sulphites or unspecified nuts retain their source wording instead of being forced into the nine tracked categories.

The chosen locations are Hawkers at 1103 N Mills Avenue, Fresh Kitchen Waterford Lakes at 851 N Alafaya Trail Q01, and Chipotle at 2211 S Orange Avenue. Census geocoding with ACS2025 geography puts all three in FL-10 for the 119th Congress. `research/district-evidence` retains the actual JSON responses. Current_Current geography returned future 120th districts during research, so the app deliberately identifies the Congress and vintage used. The user's personal district remains unconfirmed; a restaurant-address filter does not establish contestant eligibility.

## Matching without pretending to certify food

`assessDish` in `src/domain.js` compares the diner's selected canonical allergy labels with explicitly reported allergens. A positive match yields conflict. All restaurant-source entries otherwise stay unknown, even if a future malformed record says its information is complete. Missing source categories are listed separately. A source claim, vegan label, blank cell or gluten-free menu cannot establish personal suitability or lack of cross-contact.

Hawkers' guide omits wheat and tree nuts. Fresh Kitchen's almond chicken ingredient document lists eggs even though the short menu label emphasizes nuts. Its sweet potato noodles also list sesame seeds although the short label emphasizes soy. The app retains these ingredient-based positive declarations. Coconut rice and rosemary chicken notes mention coconut and mustard respectively, because the app's nine tracked categories do not represent every possible allergy. The linked original document is always the reference for needs beyond those categories.

`rankDishes` puts known conflicts after unknown entries. Preference learning never changes the allergy category. Hide conflicts only hides positive matches; it leaves unknown entries visible and labels them unknown. Nothing is labeled safe or guaranteed allergen-free.

`components/Scanner.js` resolves a local restaurant's stable slug as well as its actual ID or name. These are Verifed directory codes, not a claim that a restaurant distributes or endorses Verifed codes. `App.js` allows guests into the preference editor and coerces optional error strings to booleans before rendering, avoiding invalid text nodes inside native Views.

## Database and offline copies

The migration `20261021102254_local_orlando_catalog.sql` adds a JSON `details` column to restaurants, permits real public records, and enforces that every real restaurant stays unconnected (`confirmed=false`). It preserves the existing public-read-only policies; account/private records retain their ownership policies. The unique expression index on `body.catalogKey` makes catalog imports repeatable.

`research/seed-orlando.mjs` creates SQL from the reviewed catalog; an optional restaurant slug creates a smaller per-restaurant seed. Postgres allocates restaurant and dish UUIDs and embeds those actual IDs in dish bodies. Repeating the import updates matching stable keys, preserving favorites and references. The seeds were applied to the connected free Supabase project. `research/verify-orlando.mjs` independently reads the public REST API and checks all 110 rows against the reviewed source facts.

`mergeLocalCatalog` flattens server restaurant details and merges by restaurant slug/dish catalogKey. Live UUID records replace bundled copies. If networking fails or a row is missing, the bundled catalog remains browsable. `cloudBacked=false` prevents saving a fallback text ID into the UUID favorites table. In local demo mode, current bundled public facts replace older device-cached facts while preserving IDs; personal activity and request history remain intact.

Real restaurants have no simulated staff. Both the mobile API and database prevent kitchen requests from those entries. Call and official-source links are available instead. Fictional sample kitchens remain a separate mode for demonstrating the request/revision protocol.

## Guest preferences

`api.previewProfile` validates guest choices against the app's known options, removes duplicates, and stores the preview only in AsyncStorage on this device under its own key. It never writes a cloud profile or contacts a restaurant. Public catalog refreshes retain the preview. Signing in loads the account's own profile; it does not silently upload or substitute guest health preferences. The guest UI provides a clear-preview action.

## Tests and updating the catalog

`tests/local-catalog.test.js` checks actual saved district evidence, UUID replacement without duplicate entries, unknown classifications, ingredient evidence, ranking and cached-fact correction. `tests/api-session.test.js` additionally checks preview persistence/account separation, request rejection for real restaurants and fallback favorites. The complete native suite currently has 43 passing tests, including the five personalized-menu tests explained in DIETARY_MENUS.md.

To update menus, inspect the official live menu and linked allergen guide, edit only evidence-backed facts in the source catalog, preserve stable catalog keys, set an actual review date, regenerate and apply the seed, run the REST verification and tests, then publish a new Snack. A changed URL or elapsed review date must never be disguised as a fresh review. No automated scraping, restaurant partnership or branch kitchen verification is claimed.
